== What the code does

`pkg/glx/pixmap_linux.go` of 1.3.3:

* `offBindPixmap`, under `BindPixmap`: `glXCreatePixmap`,
  `glXBindTexImageEXT`, then `XSync` of the GL display, so that a refusal
  comes back as an X error of the call (018).
* `offRebind`, under `Rebind`: `glXReleaseTexImageEXT` and
  `glXBindTexImageEXT`, "No round trip: the X pixmap stays valid while
  bound, and an error would be counted, not fatal". 008 had measured the
  binding again with a round trip and dropped it: "binding again makes no
  round trip — the test of K4 draws the pixmap anew and binds it again, and
  the thumbnail is the new one" (research of 008). The test passed then.
* Nothing calls `glXWaitX` or waits otherwise for the X server's rendering.

`pkg/snapshot/snapshot.go`: `capture` subtracts the window's damage, then
`captureGPU` binds — a stale window: `GetGeometry`, `namePixmap`
(`NameWindowPixmap`, checked), `BindPixmap`; else `Rebind` — and
`gpu.thumbnail` draws the average and reads it back, `glReadPixels`. The
schedule (008) captures a changed window a settle of 100 ms after its first
change, or an interval after its last snapshot, whichever comes later: a
window that keeps changing is captured while its client draws.

`TestGPUThumbnail` (`pkg/snapshot/gpu_test.go`): `fillPixmap` draws an image
into a pixmap of its own through the test's xgb connection, `PutImage` in
strips of at most 200 000 bytes, each checked — a round trip; then
`BindPixmap` of `pkg/glx`, the thumbnail checked ("first"); the pixmap drawn
anew the same way, `Rebind`, the thumbnail checked again ("drawn anew").
It calls `pkg/glx` itself, not `captureGPU`.

The only bindings of pixmaps in `develop` are these two: `captureGPU` and
the test (`grep -rn 'BindPixmap\|Rebind()' --include=*.go`). The presenter
of the carousel (`pkg/carousel/present_glx*.go`) binds no pixmap: it uploads
thumbnails from memory.

== What GLX says

GLX 1.4 (https://registry.khronos.org/OpenGL/specs/gl/glx1.4.pdf), chapter
2: "Sequentiality is still guaranteed within a command stream, but not
between the X and the OpenGL command streams. It is possible, for example,
that an X command issued by a single threaded client after an OpenGL
command might be executed before that OpenGL command." And: "Synchronization
is in the hands of the client. It can be maintained with moderate cost with
the judicious use of the glFinish, glXWaitGL, glXWaitX, and XSync commands."
Section 4.4 puts `glXWaitX` in the OpenGL stream.

Section 3.3.9: "To prevent the OpenGL command sequence from executing until
any outstanding X requests are completed, call `void glXWaitX(void);` X
rendering calls made prior to glXWaitX are guaranteed to be executed before
OpenGL rendering calls made after glXWaitX. While the same result can be
achieved using XSync, glXWaitX does not require a round trip to the server,
and may therefore be more efficient. glXWaitX is ignored if there is no
current rendering context."

`GLX_EXT_texture_from_pixmap`
(https://registry.khronos.org/OpenGL/extensions/EXT/GLX_EXT_texture_from_pixmap.txt):
"The contents of the texture after the drawable has been bound are defined
as the result of all rendering that has completed before the call to
glXBindTexImageEXT." And: "no synchronization between rendering and
texturing is done by GLX. It is the application's responsibility to
implement any synchronization required." Its issue 5 has a compositing
manager run `XGrabServer()`, "glXWaitX() or XSync()", then
`glXBindTexImageEXT()`.

*Why a reply does not do.* A reply to a request — `XSync` is one — says that
the X server has executed the requests before it in the sense of the
protocol: any request after them, of any client, sees their effect, since
the X server orders its own work. The GL commands of qws are not requests
to the X server: the context is direct, and they go from qws's process to
the GPU. "The same result can be achieved using XSync" holds when the X
server's work is done by the time it answers — indirect rendering, a server
drawing on the CPU. On NVIDIA it answers with its drawing queued on the
GPU, and nothing orders that queue before the commands of qws: the test
fails with each strip of its drawing answered, and 020 found 7 of 80 passes
stale with an `XSync` of the GL display.

*Whose drawing `glXWaitX` covers.* GLX speaks of the X rendering of the
calling client, and qws draws nothing into a window's pixmap: the window's
client does, or the test's xgb connection. The X server executes the
requests of all clients in one serial order (the X protocol, quoted in
chapter 2 of GLX): a drawing whose damage the snapshotter has read, or whose
reply the test has read, is executed before anything the GL display asks
after. That `glXWaitX` makes the GL commands wait for the X server's work up
to there, whoever asked for it, is the implementation of NVIDIA, not the
letter of GLX: 020's numbers show it, and K1 and K2 here.

== The other paths

* *RENDER* (018, 022): the composites of the halvings and of the last pass
  are requests to the X server, executed after the client's drawing in its
  serial order, by the X server itself; the thumbnail comes back by
  `ShmGetImage`, whose reply is sent once the pixels are in the segment. The
  same holds for the copy of a window's rectangle out of its frame's pixmap
  (022). Nothing of the GPU of qws reads the pixmap.
* *The CPU* (`pkg/composite`): `GetImage` or `ShmGetImage`, the same.

Neither needs a wait.

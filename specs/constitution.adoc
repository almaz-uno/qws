= QWS project constitution

The set of rules a specification does not override. The specification decides
_what_ a change does; the constitution constrains _how_ it may be done, and it
applies equally to a human and to an agent.

== Document status

The constitution describes what the project actually follows, not what it
would like to follow. Every rule is backed by a place in the repository —
`AGENTS.md`, the directory layout, the `Makefile`, the documents — and can be
checked rather than taken on trust.

qws adopted spec-driven development with working code already in place: the
constitution was written against `develop` at `5997f32` (2026-06-04). Behavior
implemented before that point is described by `README.md` and `doc/`, not by
specifications, and is not re-specified retroactively; the first specification
describes a delta to that state. Issues opened before this layout (#1) get a
specification when work on them resumes. Open questions are listed as open at
the end of the document.

Amending the constitution is a separate change with its own specification: a
rule is either rewritten or withdrawn, and the specification says on what
grounds. Silently diverging from the constitution is not allowed: if the code
contradicts it, the error is either in the code or in this document, and both
cases need an explicit decision, not an omission.

== Language

The project language is English (`AGENTS.md`): documentation, comments,
commit messages, specifications, command-line help, log messages.
Identifiers, file names, configuration keys and external terms keep their
original spelling. Strings a test feeds to the program are data, not text for
a reader, and keep their language: the Cyrillic window titles of
`pkg/carousel/scenes_test.go`, on which font fallback is checked
(specification `017-english-documents`).

== Documentation is part of the change, not its consequence

A document describing the behavior of the system is updated in the same change
set that changes that behavior. A description that lags behind the code is
worse than a missing one: decisions are made from it. A document that no
longer matches the code is updated or deleted in the same change.

`specs/` holds the rationale and acceptance criteria of individual changes.
Documentation describing behavior:

* `README.md` — build, usage, features, configuration overview;
* `doc/configuration.asciidoc` — configuration keys, their sources and
  precedence;
* `config.yaml.example` — sample configuration; no test parses it, and it is
  kept in sync with `config.Default()` by hand;
* `doc/scaling-algorithms.md`, `doc/font-fallback.md` — thumbnail scaling and
  glyph-level font fallback.

Design documents: `doc/windows-switcher.asciidoc` — the architectural
decisions and the technology choices behind them; `doc/optimization.asciidoc` —
performance analysis and recommendations. A specification that overturns a
decision recorded there says so and updates the document in the same change.

== Stack and layout

* Go (version in `go.mod`), module `github.com/almaz-uno/qws`. Target — X11;
  the X protocol is spoken through `github.com/jezek/xgb`.
* The build needs cgo: the GLX presenter of the `glx` renderer (`pkg/glx`,
  `pkg/carousel/present_glx.go`) calls GLX through cgo and OpenGL through
  `go-gl/gl`, so a C toolchain, `pkg-config` and the OpenGL and X11
  development packages are required. GLFW is not used (specification
  `001-rendering-speed`).
* Command line — Cobra (`cmd/qws`: the switcher itself, `config init|show|path`,
  `version`); configuration — Viper (`internal/config`).
* `cmd/qws` — the program; `internal/config` — configuration; `pkg/<package>` —
  one package per responsibility: `carousel` (rendering, fonts), `composite`
  (thumbnail capture), `focus`, `keygrab` (with `keysyms.yaml`), `mru`, `ui`,
  `x11`.
* `console/` — standalone diagnostic programs, not part of the qws binary:
  `capture` (window capture), `glxoverlay` (the GLX presenter's mechanism
  alone), `framecmp` (criterion K3 of `001-rendering-speed`).
* Logging — zerolog, `github.com/rs/zerolog/log`, with structured fields
  instead of the standard `log` package (`AGENTS.md`).
* Build — `make build` (binary `./qws`, ignored by git, with the version of
  `git describe`), tests — `make test` (`go test ./...`), static checks —
  `make vet`, the form of `specs/` — `make check-specs`. `make lint` runs `go vet` and then `gofmt -s -w .`, which
  rewrites files in place.
* Profiling — the `--cpuprofile`, `--memprofile` and `--pprof` flags and
  `script/profile.sh`; profiles are written to `profiles/`, which is ignored by
  git.

== Configuration and user data

* qws keeps no state of its own between runs. The only persistent data it
  reads is the user's configuration: the file `~/.config/qws/config.yaml` (or
  `config.yaml` in `$HOME`, or the one given by `--config`), `QWS_*`
  environment variables and flags. Precedence: flags, then environment, then
  file, then defaults.
* Default values have a single source — `config.Default()`
  (`internal/config/config.go`); `qws config init` writes a file from it. A
  default is changed there, and the documents quoting it are changed in the
  same change set.
* Configuration files belong to users and outlive program versions. Viper
  reads them with `Unmarshal`, which ignores unknown keys: a renamed or removed
  key does not fail, it silently falls back to the default. A change that
  renames, removes or reinterprets a key, an environment variable or a flag
  therefore says in its specification what happens to existing
  configurations — the old name is kept as an alias, reported, or knowingly
  dropped.

== Verifiability

Tests are updated together with the implementation — in the same change, not
"later". `make check-specs`, `go vet ./...` and `go test ./...` pass locally
before a change is proposed for commit, and run in GitHub Actions — workflow `test`, in Debian 12
with the packages of `scripts/debian-deps.sh` — on every push of a branch and
every pull request; the same workflow gates the release (specification
`004-releases`). At the time of writing, tests exist for `internal/config`,
`internal/relnotes`, `pkg/carousel` (font fallback) and `pkg/mru`.

Tests do not need an X server, a compositor, a window manager or a GPU. A test
that depends on a resource of the host system skips when the resource is
absent rather than failing (`TestMultiFallbackFace_Creation` skips without
system fonts). Behavior that can only be observed under X11 — key grabs,
compositing, rendering, focus — is checked by a manual scenario written in the
specification: window manager, compositor on or off, renderer, steps and the
expected observable result.

== Decisions rest on measurements

An acceptance criterion says what is checked and how: a number with its
measurement method, a named test, or a reproducible manual scenario with an
observable result. "Works better", "faster", "looks right" are not criteria
and do not enter a specification in that form.

The numbers a decision rests on are reproducible: the specification says on
what data and how they were obtained, so that the next reader can repeat or
refute them instead of trusting a retelling. For performance this means the
conditions the figures depend on: machine and GPU, window manager, compositor,
renderer, number of windows and monitors, thumbnail size and scaling
algorithm.

A decision not yet made is recorded as open. A specification that hides an
unresolved choice behind a plausible default is worse than one that admits it.

== Secrets

There are no secrets in the repository, and qws needs none. Should a change
introduce one, the local value stays outside git, and the repository holds
only an example with empty values.

== Working with history

The agent does not run `git commit`, `push`, create tags or branches for a
commit without the author's explicit agreement — even when the task looks
finished. Model co-authorship (`Co-Authored-By`, "Generated with…") is not
added to commit messages or pull request descriptions.

Commit messages follow the style of the history: a gitmoji, then a
Conventional Commits type and a summary — `✨ feat:`, `🐛 fix:`, `📝 docs:`,
`♻️ refactor:`, `⚡ perf:`. Work happens on `issue/qws#NN-slug` branches off
`develop` and lands through a GitHub pull request into `develop`.

== Releases and versions

The section is introduced by specification `004-releases`; the rule on the
major version by `006-major-version`.

* A version is an annotated tag `vX.Y.Z` on `develop`; `make build` takes it
  from `git describe` into `qws version`.
* The minor version for new behaviour, a new configuration key or a changed
  default; the patch for fixes without new behaviour.
* The major version when a release is incompatible with the previous ones —
  a configuration they read is not read the same way, a key, a flag or an
  environment variable is removed or changes its meaning without an alias —
  but always by agreement with the author: without it such a change goes out
  as a minor version. Or by the author's direct request: 1.0.0, planned
  after the animation (2026-10-01).
* `RELEASE-NOTES.adoc`: a minor or major release is a chapter, its patches
  are subsections, the newest come first.
* Every version tag gets a GitHub release, built by GitHub Actions
  (`.github/workflows/release.yml`) when the tag is pushed: the checks on the
  tag, then `make release TAG=vX.Y.Z` (`scripts/release.sh`). A pushed tag
  without a release is released by `gh workflow run release -f
  tag=vX.Y.Z`; `make release` on the author's machine is the same script.
  The files are built from the tag in a temporary `git worktree`, in Debian
  12, for `linux-amd64`; the text is the section of the notes at the tag.
* Tags, their push and releases only with the author's consent (section
  "Working with history"): the script neither creates nor pushes a tag, and
  pushing a tag is the consent to release it.

== Specifications

The section is introduced by specification `009-spec-checks`.

* The layout of `specs/` is the project's own, described in
  `specs/README.adoc`. No external framework of spec-driven development —
  OpenSpec, GSD, Spec Kit — is adopted: each brings Markdown among AsciiDoc
  documents, directories and commands of its own and a release cycle the
  project does not control. A description of the current behavior is
  `README.md` and `doc/`, not specifications.
* A specification does not copy what git and GitHub hold — whether the
  change is merged or released, whether its issue is closed: such a fact
  arrives after the last commit of the change and cannot be written in it.
* The form of `specs/` is checked by `make check-specs` before a change is
  proposed and in workflow `test`. The check sees the form, not the truth:
  that a specification matches the code rests on its criteria (section
  "Decisions rest on measurements").

== What the constitution does not regulate

Open questions, recorded as open. Each is closed by a separate change with a
specification, after which the corresponding section appears above.

* *Window contents* — qws reads titles, icons and pixels of the user's windows
  in order to display them; there is no rule yet on whether they may be
  logged, written to disk or sent anywhere.

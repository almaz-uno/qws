== What the specifications allow

*Sharing.* `GLX_ARB_create_context`: with a share context, "all shareable
data (excluding OpenGL texture objects named 0) will be shared"; the server
context state of all sharing contexts "must exist in a single address
space", else, or when the share context was created on another screen,
`BadMatch`. Two direct contexts of one process share an address space. The
extension says nothing of the Xlib display a context is created on; NVIDIA
shares between displays (the probe).

*What is shared*
(https://registry.khronos.org/OpenGL/specs/gl/glspec46.core.pdf[OpenGL 4.6
core], chapter 5): buffer, program, shader,
renderbuffer, sampler, sync and texture objects; not the containers —
framebuffers, vertex arrays. A deleted texture lives on while it is bound in
any context (5.1.3); the commands of another context still in flight are not
named there.

*When a change is seen* (5.3): the contents of an object changed in another
context are seen once the change has completed — by `glFinish`, or by
`glFenceSync` there and `glWaitSync` here — and the object is bound again in
the current context (rule 4). The presenter binds the textures of a frame at
every draw.

*Fences* (4.1): `glClientWaitSync` with a timeout of 0 tests the state of a
fence without blocking; `glWaitSync` makes the server wait, "either in the
CPU executing server-side code, or in the GPU hardware", and returns at once.
A fence waited for from another context signals only once flushed in its
own: `SYNC_FLUSH_COMMANDS_BIT` "will not help when waiting for a fence
command issued in another context's command stream" (4.1.2).

*NVIDIA.*
https://developer.download.nvidia.com/GTC/PDF/GTC2012/PresentationPDF/S0356-GTC2012-Texture-Transfers.pdf["Optimizing
Texture Transfers"], GTC 2012, S0356: since Fermi the
GPU has copy engines, one on a GeForce, that move data beside rendering;
OpenGL gets them for transfers made from a context of their own on a thread
of their own, synchronized with the rendering context by `ARB_sync`.
Non-transfer calls in the transfer thread may serialize it with rendering,
and the driver then says "Pixel transfer is synchronized with 3D rendering"
in its debug output. On
https://forums.developer.nvidia.com/t/gltexstorage-and-multiple-gl-contexts/45183[NVIDIA's
forum], a texture allocated in one context and filled in another came out
corrupted: allocation and upload belong in the one upload context, fenced,
the rendering context waiting for the fence before it draws.

== The probe

`~/.cache/qws-probe-upload/v2`: an override-redirect window of 2520×1400, the
overlay of E1, mapped off the screen, with the context of `pkg/glx`, swap
interval 0; a scene of a base of the window size and 23 layers of 560×640,
blended and moving a little each frame; frames due every 1/144 s, the last
3 ms spun, each a swap and `glFinish`, as frames are while their timings are
logged. In every second pause, no later than 3 ms before the frame:
alternately a layer of 1.4 MB into a new texture, as `SetLayer` does, or a
piece of 64 rows of a frame, 630 KB, through a pixel buffer, as `StageFrame`
does, a frame staged starting with a copy of the base into the staging
texture. Modes:

* `none` — no uploads;
* `same` — the uploads in the presenter's context, the layers from the
  memory of the process, as in 1.2.0; `samepbo` — the layers through a pixel
  buffer;
* `shared` — the same uploads made by a second context on a thread of its
  own, created with the presenter's as share context on a pbuffer of 1×1, a
  fence after each; the presenter draws a new layer once `glClientWaitSync`
  with timeout 0 finds its fence signalled, the copy waits for a fence of the
  presenter's frames; `sharedpbo` — the layers through the second context's
  pixel buffer;
* `flood`, `floodpbo` — the second context uploading layers into textures no
  frame draws, without pause, from memory or through its pixel buffer.

The modes take turns in blocks of 400 frames, the first 10 of a block not
counted: run one after another, 9900 frames each, they drifted with the
desktop — a run of `shared` in which no frame drew a layer before its fence
missed 1.1 % of its intervals, the runs before and after it 0–0.02 %. Timer
queries give the time of a frame on the GPU, from its first command to the
end of its swap, and how long its first command waited there after it was
issued, "queued".

. *Sharing works* on E1: the second context, on an Xlib display of its own
  or on the presenter's (`XInitThreads` first), is created with the
  presenter's as share context, and the layers it uploads show in the
  presenter's frames.
. *No serialization reported.* With both contexts debug contexts, NVIDIA
  reports only that the pixel buffer is in system memory and mapped
  write-only, "fast"; never "synchronized with 3D rendering".
. *An upload in the second context*, from the request to its fence
  signalled: a layer 1.1–1.4 ms at the median, issued in 0.27–0.62 ms of the
  uploader's CPU; a piece 0.5 ms, issued in 0.13 ms — some 1.2 GB/s. No layer
  had to be drawn before its fence signalled: by the next frame, 3 ms later
  at least, it had.
. *Transfers beside the frames.* Flooding, the frames themselves take as
  long on the GPU as without uploads, but start later: the GPU turns to the
  presenter's commands once the transfer under way is done. From memory they
  start a millisecond late; through a pixel buffer, a fifth of that:

== What and why

The constitution leaves the SDD framework open: OpenSpec, GSD, Spec Kit or a
layout of our own. The author keeps the project's own layout (2026-10-01):
it works — specifications 001–007 and release 1.0.0 went through it — and
simplicity is a condition of its reliability.

Reliability is what the layout lacks: its form rests on discipline, and the
discipline already fails. `:status:` of 001, 002 and 005 says "not merged",
while their pull requests #6, #11 and #12 were merged. The cause is not
negligence: `:status:` is free text that mixes three things — the stage of the
change, how its criteria are met, which section "Results" already says, and
facts git and GitHub hold, such as "merged" and "released". A merge happens
after the last commit of the change it merges, so it cannot be written in that
change: such a status lags behind or needs a commit after the merge, as 007
did (`fb23f58`).

The change:

. closes the open question: the layout stays the project's own;
. `:status:` takes one of three values, each set within the change it
  describes;
. the form of `specs/` is checked mechanically, locally and in workflow
  `test`.

The same change is made in siphon and lxqt-weather, with the same check.

Unchanged: the program; the documents of a change and when each is needed;
the numbering of directories; the order of issue, branch and specification;
the content of specifications 001–007 except `:status:`.

== Decisions

* *No external framework.* Each of the three brings Markdown among AsciiDoc
  documents, directories and commands of its own and a release cycle the
  project does not control. None removes a failure the project has: the
  status that lags behind would lag behind in any of them.
* *No specifications of the current state.* OpenSpec keeps a description of
  the current behavior next to the changes; in qws that role is played by
  `README.md` and `doc/`, kept up to date by the constitution (section
  "Documentation is part of the change, not its consequence"). A second
  description of the same behavior is a second source of truth.
* *Three values of `:status:`*, each set within the change: `draft`,
  `implemented`, `dropped`. Since the specification and the code reach
  `develop` in one merge, `implemented` on `develop` means the code is
  there — by construction, not by someone remembering. The values are the
  same English words in the three projects: they are identifiers, like
  configuration keys, and the check is the same.
* *`:issue:` in every specification*, `draft` included: the issue comes
  first (`specs/README.adoc`, "Relation to issues"), so a committed
  specification always has its number.
* *No test of the check.* A test, `scripts/check-specs-test.sh` with nine
  cases, and `mutate.sh`, which broke the check one rule at a time to see the
  test fail, were written and removed by the author's decision (2026-10-01):
  some 90 lines of test guarding some 60 of check are more complex than what
  they guard. The check is short enough to be read; a change to it is tried
  by hand on a copy of `specs/` with each violation (K2).
* *A shell script, not a Go test.* lxqt-weather is C++, and one check for
  three projects is one logic to read. The copies differ in the heading of
  the results section and in what `:issue:` holds — siphon has no tracker
  yet — and siphon's speaks Russian, the language of that project.
* *What is not checked.* The check sees the form, not the truth: that a
  specification matches the code rests on criteria that name a test, a
  measurement or a reproducible scenario (constitution, "Decisions rest on
  measurements"). Neither are checked `:revdate:` — its presence says nothing
  of its correctness — nor gaps in the numbering: 003 was never used, and a
  gap misleads no one.

== Behavior

`make check-specs` runs `scripts/check-specs.sh`. The check passes when:

* every entry of `specs/` is `README.adoc`, `constitution.adoc` or a
  directory `NNN-slug` — three digits, a hyphen, lowercase words of letters
  and digits joined by hyphens;
* no two directories share a number;
* every directory has `spec.adoc`;
* the header of `spec.adoc` — the lines before the first empty one — has
  `:status:` equal to `draft`, `implemented` or `dropped`, and `:issue:`
  with the number of an issue;
* an `implemented` specification has the section `== Results`.

Each violation is printed as a line `specs/<path>: <what is wrong>`; the exit
status is 1 if there is any. Workflow `test` runs `make check-specs` before
`make vet`. It checks the merge of a pull request with `develop`, so two
branches that took the same number are caught on the second pull request.

== Constitution

A section "Specifications" is added after "Releases and versions":

* The layout of `specs/` is the project's own, described in
  `specs/README.adoc`. No external framework of spec-driven development —
  OpenSpec, GSD, Spec Kit — is adopted: each brings Markdown among AsciiDoc
  documents, directories and commands of its own and a release cycle the
  project does not control. A description of the current behavior is
  `README.md` and `doc/`, not specifications.
* A specification does not copy what git and GitHub hold — whether the
  change is merged or released, whether its issue is closed: such a fact
  arrives after the last commit of the change and cannot be written in it.
* The form of `specs/` is checked by `make check-specs` before a change is
  proposed and in workflow `test`. The check sees the form, not the truth:
  that a specification matches the code rests on its criteria (section
  "Decisions rest on measurements").

Section "Verifiability" names `make check-specs` among the checks that pass
before a change is proposed; section "Stack and layout" names it among the
`Makefile` targets. The open question "SDD framework" is removed.

== `specs/README.adoc`

The rule on `:status:` is rewritten: `spec.adoc` carries `:issue:` and
`:status:` — `draft` (nothing implemented), `implemented` (implemented, and
section "Results" says how each criterion is met) or `dropped` (abandoned,
and the specification says why); whether the change is merged or released is
told by git and GitHub, how it was measured — by "Results". Section "Layout"
says that `make check-specs` checks the form of the directory and lists what
it checks.

Found while this change was merged (section "Results"): "Relation to issues"
gets a step — a pull request whose specification is not yet `implemented` is
opened as a draft and marked ready with the commit that writes its results.

== What and why

A connection of qws can run out of resource identifiers, XIDs, and from
then on make no resource of the X server: no pixmap, picture or GC of a
snapshot by RENDER, no damage object of a new window (issue #70). Not seen
yet — the service restarts at every login — but latent in every release
since 1.1.0 for the RENDER paths of 018 and 022.

The cause, confirmed by the code of xgb and by a test that reproduces it
(research): xgb 1.3.1 gives the XIDs of a connection in turn within the
resource-id-mask the X server gave it, and once it has given the last one
asks the range function of the connection for more; without one — and qws
sets none — `NewId` fails from then on with "there are no more available
resource identifiers, and no re-use configured", whatever the connection
has freed meanwhile. On E1 the mask is `0x1fffff`: 2 097 151 XIDs a
connection. The snapshotter's connection takes 9 for a snapshot by RENDER
of a window of 2560×1440 drawn into its frame (022, two halvings), 7 for one
with a pixmap of its own (018), one for each pixmap it names and each window
it follows. A window of that size that changes all the time, captured once a
second, uses the snapshotter's connection up in 2 097 151 / 9 s, some 2.7
days.

The change: every connection `x11.NewConn` makes (021) gets a range function
that asks the X server for a range of XIDs of the connection that name no
resource, by `GetXIDRange` of the extension XC-MISC, which X.Org's servers
have and xgb implements (`xcmisc`). XC-MISC is set up once per process with
the other extensions of 021, never initialised on a live connection.

The specification is a delta to `develop` at `9774075` (1.3.3); the change
goes out as patch 1.3.4, a fix with no new behaviour. Unchanged: the
connections qws makes, all through `x11.NewConn`, and the order
`cmd/qws/root.go` makes them in; the extensions each part uses and what it
falls back to without them; the first range of every connection, the XIDs
xgb gives before it needs a range function; the configuration — no key,
variable or flag changes. The console programs `framecmp` and `glxoverlay`
keep `xgb.NewConn` and no reuse: they live for a run of their own. The
connections of Xlib in `pkg/glx` take their XIDs from libxcb, which reuses
them through XC-MISC already (research).

== Decisions

Asked for, 2026-10-03 (issue #70):

* XIDs reused on every connection of the program, through `GetXIDRange` of
  XC-MISC, set where every connection is made: `x11.NewConn`;
* a test that goes through a whole range.

Made on the way, 2026-10-03, for the author to confirm:

* *XC-MISC among the extensions of the setup.* `extensionNames` of
  `pkg/x11/extensions.go` gets XC-MISC: the setup asks for it with the
  other six and every connection gets its opcode, so that its requests can
  be sent with no `xcmisc.Init`, which 021 leaves out of qws. XC-MISC has
  no events and no errors: the tables of events and errors stay as 021
  writes them.
* *Without XC-MISC, today's behaviour.* `NewConn` sets no range function,
  and the setup, run once per process, logs a warning once: "XC-MISC
  unavailable, XIDs not reused".
* *The answer of none.* X.Org's server answers start 0 and count 1 when no
  XID of the client is free, which xgb would take for a range of one XID,
  0 ORed with the base, in use: the range function returns an error instead,
  and `NewId` fails, as libxcb does (research).
* *The test takes the XIDs alone.* A pixmap made and freed with every XID
  of a range costs E1 15 s, 13.5 s of them the X server's CPU, at every
  `go test ./...` with a display, on the author's desktop that of the
  desktop. `TestXIDsReused` asks for the XIDs of the whole first range and
  past it, keeps pixmaps with some of the first, and makes pixmaps, checked,
  with some of those past it; the flag `-xid-requests` of the test binary
  makes and frees a pixmap with every one (research, "Reproduction").
* *The XIDs in flight are not guarded against* — an open decision: xgb
  gives up to five XIDs ahead, which the X server may take for free when it
  answers `GetXIDRange` and give again once the next range is walked through
  (research, "XIDs in flight").

== Behavior

. *The setup.* The first `x11.NewConn` of the process asks `QueryExtension`
  for XC-MISC with Composite, DAMAGE, MIT-SHM, RANDR, RENDER and XFIXES
  (021). Without XC-MISC it logs the warning.
. *Connections.* Every connection `x11.NewConn` makes gets the opcode of
  XC-MISC and, when the X server has it, the range function.
. *Past the first range.* When xgb has given every XID of a range, it calls
  the range function, which asks `GetXIDRange` and returns the range of the
  reply; xgb gives its XIDs in turn and asks again past its end. On the
  answer of none, `NewId` fails with "error getting ID re-use: XC-MISC:
  every XID of the connection in use".
. *Without XC-MISC*, `NewId` fails past the first range, as before.

== Open decisions

. *XIDs in flight.* xgb gives up to five XIDs ahead of `NewId`, and asks
  for a range right after it has given the last of the one before, while
  the XIDs waiting and the one taken last may not have reached the X server
  yet: its range can hold them, and once xgb has walked through it it gives
  them again. A resource still named by one — a damage object, a pixmap
  named — then fails to be made with BadIDChoice, and a `FreePixmap` of
  the RENDER path after it frees the pixmap of that XID (research, "XIDs in
  flight"). A remedy: the range function cuts from the X server's range the
  last 64 XIDs of the range it gave before; not taken without the author.
. Upstream: `generateXIds` of xgb 1.3.1 says it "needs to be updated to use
  the XC Misc extension once we run out of new ids". A report, or a patch
  that would set the function in xgb, is the author's decision.
. `TestXIDsReused` takes 0.5 s, 1.6 s under `-race`, at every `go test
  ./...` with a display; the X server spends some 0.02 s of CPU on it.
